# pi-acp core

## Goal

Add `crates/pi-acp`, an ACP v2 bridge that runs one `pi --mode rpc` process
per session and meets the turn model `oxd` requires: a prompt is answered
with its `messageId` when Pi accepts it, `user_message` and `state_update`
drive the turn, and the session reports `background: []` so it can park.
This is task 2 of `.agents/scratch/pi.md`; resume and replay (task 3),
config options and commands (task 4), elicitations (task 5), and the smoke
check and protocol docs (task 6) follow it.

**Brief:** `.agents/scratch/pi.md`, section "2. pi-acp core"

## Related code

  copies: `Agent.v2()` with one `on_receive_request` per method.
- `crates/claude-code-acp/src/bridge.rs` — `new_session` answers, then
  reports idle, then starts the native process; `prompt` sends the prompt
  before returning so a following cancel stays after it.
- `crates/claude-code-acp/src/runner.rs` — the process pattern to follow:
  an unbounded channel feeding a stdin writer task, an `Output` reader that
  splits stdout on LF, `Stderr` collection, `drain` and `read_buffered` for
  output left in the pipe at exit, and failing the open turn and waiting
  prompts when the process exits.

  session is idle, so a prompt reaches Pi while it works only when Pi

  beside the app's executable.

## Decisions

- **Pi facts relied on**, checked in the installed 1.4.0 source:
  - `prompt` answers `{"disposition":"started"|"queued"|"handled"}` or
    `success:false` with `error`. `started` is sent before `agent_start`.
    `streamingBehavior` is ignored while Pi is idle, so the bridge always
    sends `"followUp"`.
  - `abort` sets the abort flag only once a run has started; an `abort` that
    arrives while a prompt is still in preflight does not stop the run that
    prompt then starts.
  - `agent_settled {aborted}` follows the last `agent_end`; `agent_end`
    comes before retries and does not end the turn.
  - `--session-id` accepts `[A-Za-z0-9][A-Za-z0-9._-]*[A-Za-z0-9]`, opens the
    project session with that ID, or creates it.
  - Assistant messages end with `stopReason` `stop`, `length`, `toolUse`,
    `error` (with `errorMessage`), or `aborted`.
  - `edit` takes `{path, edits:[{oldText,newText}]}` and its result's
    `details.patch` is a jsdiff unified patch with `--- path` and
    `+++ path` headers. `write` takes `{path, content}`.
- **Sessions are in memory.** `Bridge` holds `Mutex<HashMap<String,
  Session>>`; `Session` has `cwd`, `pi_session_id`, `title`, and
  `pi: Option<Pi>`. The ACP session ID is `Uuid::new_v4().simple()` as in
  `claude-code-acp`; `pi_session_id` is a separate hyphenated UUID v4.
  Every Pi start passes `--session-id <pi_session_id>`, so a Pi restarted
  after an exit continues the same Pi session. Task 3 persists `Session`.
- **Pi starts** as `pi --mode rpc --approve --session-id <id>` in the
  session's `cwd`, with piped stdio and `kill_on_drop`, right after the
  `session/new` response and the idle `state_update`. A spawn failure is
  logged, and `prompt` tries again and fails with the error.
- **Commands** carry string IDs from a per-process counter. `Pi` keeps a
  `pending: HashMap<String, Pending>` with `Pending::Prompt(Prompt)` (the
  ACP `messageId`, prompt blocks, and `Responder`) and `Pending::Abort`.
  A response without a known ID is logged.
- **Prompt acceptance:**
  - `started` or `queued`: answer the responder with the `messageId`, send
    `user_message` with the ACP prompt blocks, then `running`.
  - `handled`: the same, then, if no run is active, `idle` with `end_turn`.
    A run the extension command starts is its own turn.
  - `success:false`: answer the responder with `-32603` and Pi's `error`;
    no `user_message`.
- **Cancel** sends `abort`. When a prompt is still awaiting Pi's answer,
  `Pi` sets `abort_on_start`, and sends a second `abort` when that prompt is
  answered `started` or `queued`.
- **Turn end.** `agent_start` reports `running` if not already. At
  `agent_settled`, open tool calls are failed and `idle` is sent with:
  `cancelled` when `aborted`; else `error` with the last assistant
  message's `errorMessage` when its `stopReason` is `error`; else
  `max_tokens` for `length`; else `end_turn`. Every state update carries
  `background: []`.
- **Streaming.** At an assistant `message_start` the block map resets.
  `text_start` and `thinking_start` give `contentIndex` a new `messageId`;
  `text_delta` and `thinking_delta` send `agent_message_chunk` and
  `agent_thought_chunk` under it. At the assistant `message_end`, a text or
  thinking block that streamed nothing and is not empty is sent whole as
  `agent_message` or `agent_thought`, and each `toolCall` block opens a tool
  call. Pi's own user and tool-result messages are not forwarded.
- **Tool calls** (`tools.rs`):
  - Opened at `message_end` with `pending` status, `name`, `title`,
    `kind`, `raw_input`, and `locations`.
  - Kinds: `read` and `ls` are `read`; `edit` and `write` are `edit`;
    `grep` and `find` are `search`; `bash` is `execute`; anything else is
    `other`.
  - Title: the tool name capitalized, followed by its argument as a code
    span: `command` for `bash`, `pattern` for `grep` and `find`, `path`
    otherwise. A tool without one is titled with its name.
  - Locations: a `path` argument resolved against the session's `cwd`;
    `read` adds `line` from `offset`.
  - `tool_execution_start` sets `in_progress`. `tool_execution_end` sets
    `completed`, or `failed` when `isError`, and the whole `content`: the
    result's text and image blocks, preceded for a successful `edit` or
    `write` by a `Diff`.
  - `edit`'s `Diff` is a `modify` change with the patch converted to ACP's
    `git_patch` format: the jsdiff header lines are replaced by
    `diff --git <abs> <abs>`, `--- <abs>`, `+++ <abs>`.
  - `write`'s `Diff` is an `add` change with a generated new-file patch
    (`--- /dev/null`, one `+` line per content line) when the path did not
    exist when the tool call opened, and a `modify` change without patch
    text otherwise.
- **Extension dialogs.** An `extension_ui_request` whose `method` is
  `select`, `confirm`, `input`, or `editor` is answered at once with
  `{"type":"extension_ui_response","id":…,"cancelled":true}`. Other methods
  are ignored. Task 5 replaces this with form elicitations.
- **Exit.** When Pi exits, `Pi` records why (`pi exited with <status>:
  <stderr>`), fails each waiting prompt with that error, and ends an
  active turn with `error` and that message, or `cancelled` when the
  session is closing. The next `session/prompt` starts Pi again.
- **Close** removes the session, sends `abort`, drops the command sender so
  Pi's stdin closes, and answers once Pi has exited. Later requests for the
  session get `session_not_found`.
- **Initialize** answers with the client's protocol version and
  `session.prompt.image`. `session/new` with MCP servers is rejected with
  `-32602`.
- **Prompt content** (`content.rs`): text blocks and resource links (as
  `[@name](uri)`) join with `\n` into `message`; images become
  `images: [{type:"image", data, mimeType}]`; an empty prompt, audio, and
  embedded resources are rejected with `-32602`. The first prompt with text
  titles the session as in `claude-code-acp`.
- **Duplication.** `Stderr`, `drain`, `read_buffered`, `validation::cwd`,
  `notify`, `state_update`, and `code_span` are copied from
  `claude-code-acp` rather than moved into a shared crate; the two bridges
  share no other code.

## Check your assumptions

1. **Parking before resume exists.** Kept.
   - **Decided:** Report `background: []` now, as the notes specify, though
     `session/resume` arrives in task 3.
   - **Consequences:** Until task 3 lands, a Pi session idle and unviewed
     for 15 minutes, or loaded after a daemon restart, fails to load
     because `pi-acp` has no `session/resume`.
   - **Alternative:** Omit the `background` list until task 3, so `oxd`
     never parks Pi sessions.
   - **Trade-offs:** `[]` matches the final behavior and keeps this change
     as the notes describe; omitting the list keeps interim sessions usable
     at the cost of a line task 3 must change.

2. **Pi version checked against.** Kept.
   - **Decided:** Pi 1.4.0, the only Pi installed (`/opt/homebrew/bin/pi`,
     an npm install). The 1.5.2 managed install the notes describe is not on
     this machine.
   - **Consequences:** The fake `pi` in the tests copies 1.4.0's records.
     Differences in 1.5.2 show up only in task 6's live smoke check.
   - **Alternative:** Install Pi 1.5.2 and recheck the facts in Decisions
     before implementing.
   - **Trade-offs:** Planning against 1.4.0 proceeds now on verified
     source; rechecking costs an install and catches protocol drift before
     the bridge is written.

3. **Extension dialogs before task 5.** Kept.
   - **Decided:** Answer every `select`, `confirm`, `input`, and `editor`
     request with `cancelled: true`, so no turn waits on a dialog.
   - **Consequences:** A project extension that asks before acting, such
     as a tool gate calling `ctx.ui.confirm`, sees `false` or `undefined`
     and blocks the action.
   - **Alternative:** Leave requests unanswered until task 5.
   - **Trade-offs:** Dismissing keeps turns finishing; leaving them open
     hangs any turn that triggers a dialog until the user cancels it.

4. **No `ox` MCP server for Pi.** Kept.
   - **Decided:** `pi-acp` does not advertise `session.mcp.stdio`, so `oxd`
     does not pass `ox-mcp`, and the bridge titles a session from its first
     prompt as `claude-code-acp` does.
   - **Consequences:** Pi cannot call the `ox` tools, so it cannot set the
     session title itself.
   - **Alternative:** Advertise `session.mcp.stdio` and hand the servers to
     Pi through a bundled extension calling `registerMcpServer`.
   - **Trade-offs:** No MCP keeps the bridge to the notes' scope; the
     extension gives Pi parity with Claude at the cost of shipping and
     loading a Pi extension.

5. **Prompts an extension command handles.** Kept.
   - **Decided:** A prompt Pi answers `handled` is answered with its
     `messageId`, shown as a user message, and ends its turn with
     `end_turn` unless a run is active.
   - **Consequences:** Typing an extension command such as `/foo` shows it
     in the conversation as a prompt with an empty turn; any output the
     command starts arrives as a turn of its own.
   - **Alternative:** Answer a handled prompt with an error, so it shows as
     a failed turn.
   - **Trade-offs:** Echoing treats commands as ordinary input and matches
     how they run in Pi; an error marks that Pi did not take the text into
     the conversation but reads as a failure.

## Test plan

`crates/pi-acp/tests/protocol.rs` runs the bridge against a fake `pi`, a
`#!/bin/sh` script on a prepended `PATH` that appends `$*` and `pwd` to a
`calls` file, reads commands with `IFS= read -r`, and prints Pi's records.
Each test gets its own temporary directory.

- `a_new_session_starts_pi_and_reports_idle`: `session/new` is answered,
  then `idle` with `background: []`; `calls` shows
  `--mode rpc --approve --session-id <uuid>` run in the project.
- `a_prompt_is_answered_when_pi_accepts_it_and_ends_when_pi_settles`: the
  response's `messageId` matches the `user_message`; text and thinking
  deltas arrive as chunks under one `messageId` per block; an
  `agent_end {willRetry:true}` followed by `auto_retry_start`, a second
  run's text, `agent_end`, and `agent_settled` yields exactly one `idle`,
  with `end_turn`, after the second run's text; the prompt reached Pi with
  `streamingBehavior: "followUp"`.
- `tool_calls_report_kinds_locations_and_diffs`: an assistant message with
  `edit`, `write` (new file), and `bash` calls, then their executions.
  `edit` is kind `edit` with its absolute path as location, goes
  `pending`, `in_progress`, `completed`, and ends with a `diff` whose patch
  starts `diff --git <abs> <abs>`; `write` has an `add` change with a
  `/dev/null` patch; `bash` is kind `execute` and ends `failed` with its
  output.
- `a_prompt_pi_rejects_fails_with_its_error`: `success:false` answers the
  prompt with `-32603` and Pi's message, and no `user_message` is sent.
- `a_failed_response_ends_the_turn_with_its_error`: an assistant
  `message_end` with `stopReason: "error"` ends the turn with `error` and
  its `errorMessage`.
- `cancel_aborts_the_turn`: `session/cancel` during a run sends `abort`,
  and `agent_settled {aborted:true}` ends the turn `cancelled`.
- `cancel_sent_right_after_prompt_cancels_it`: prompt and cancel written
  together; the fake reads both before answering `started`, then expects a
  second `abort`; the turn ends `cancelled`.
- `a_pi_that_exits_fails_the_turn_and_the_next_prompt_starts_it_again`: the
  first Pi writes to stderr and exits mid-turn, ending the turn with
  `error` carrying the stderr text; the next prompt starts a second Pi with
  the same `--session-id` and ends `end_turn`.
- `closing_a_session_stops_pi`: `session/close` is answered after the fake
  sees stdin close and exits; a later prompt gets `session_not_found`.
- `extension_dialogs_are_dismissed`: a `confirm` request is answered with
  `cancelled: true` and its ID, a `notify` gets no answer, and the turn
  ends `end_turn`.
- `a_handled_prompt_ends_its_turn`: disposition `handled` answers the
  prompt, sends `user_message`, and ends the turn `end_turn`.

## Implementation plan

1. `crates/pi-acp/Cargo.toml`: package `pi-acp`, edition 2024, MIT,
   `[lints] workspace = true`; dependencies `agent-client-protocol =5.2.0`
   (`stdio`, `unstable_protocol_v2`), `serde_json`, `tokio` (`macros`,
   `rt-multi-thread`, `process`, `io-util`, `sync`), `uuid` (`v4`), `libc`;
   dev-dependencies `serde_json`, `tempfile`, `tokio`. The workspace's
   `crates/*` glob picks it up.
2. `crates/pi-acp/src/validation.rs`: `cwd`, from `claude-code-acp`.
3. `crates/pi-acp/src/content.rs`: `pi_prompt(&[ContentBlock]) ->
   Result<(String, Vec<Value>), String>` and `prompt_text`.
4. `crates/pi-acp/src/tools.rs`: `kind`, `title`, `locations`, and
   `diff(name, args, details, cwd, existed) -> Option<ToolCallContent>`
   with `git_patch` (header rewrite) and `new_file_patch`.
5. `crates/pi-acp/src/updates.rs`: `Updates` for one session: `working`,
   `idle(StopReason)`, `is_working`, `user_message`, `text_chunk`,
   `thought_chunk`, `message`, `thought`, `open_tool`, `tool_started`,
   `tool_ended`, `fail_open_tools`; `state_update`, `idle_state`, `notify`.
6. `crates/pi-acp/src/pi.rs`: `Pi::start(cwd, pi_session_id, updates)`,
   `prompt`, `abort`, `stop`, `has_exited`; the stdin writer task; `Output`
   reading stdout, dispatching responses, events, and
   `extension_ui_request`, tracking the block map, open tools' `existed`
   flags, and the last assistant `stopReason`; `Stderr`, `drain`, and
   `read_buffered`; exit handling.
7. `crates/pi-acp/src/bridge.rs`: `Bridge` with `initialize`,
   `new_session`, `start_new`, `prompt`, `cancel`, `close_session`, and
   `start_pi`.
8. `crates/pi-acp/src/main.rs`: wiring for `initialize`, `session/new`
   (respond, send idle, `start_new`), `session/prompt`, `session/close`,
   and the `session/cancel` notification.
9. `crates/pi-acp/tests/protocol.rs`: the tests above.
10. `Makefile`: add `-p pi-acp` to the `cargo build` lines of `dev` and
    `install`, and `pi-acp` to `install`'s `cp` and `codesign` loop.

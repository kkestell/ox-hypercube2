# Pi sessions get the ox MCP server

## Goal

`pi-acp` declares no MCP capability and refuses MCP servers in `session/new` and `session/resume`, so `oxd` never gives Pi the `ox` server and Pi's instructions leave out the `ox` tools. After this change `pi-acp` declares stdio MCP support, keeps the client's stdio servers on the session, and has every Pi it starts register them through an extension embedded in the binary. The model sees `set_title` and `post_status_update` as ordinary tools, and a Pi session can title itself and post status updates like a Claude session.

## Related code

- `crates/pi-acp/src/bridge.rs`: `initialize` declares the session capabilities. `new_session` and `resume_session` refuse non-empty `mcp_servers`. `Session` holds what every Pi start needs. `start_pi` passes it to `Pi::start` for a new session, a resumed one, and a Pi restarted after it exited.
- `crates/pi-acp/src/pi.rs`: `Pi::start` builds the `pi --mode rpc --approve --session-id <id>` command.
- `crates/claude-code-acp/src/bridge.rs`: `initialize` declares `.mcp(acp::McpCapabilities::new().stdio(acp::McpStdioCapabilities::new()))`. `parse_mcp` refuses non-stdio servers and relative commands, and converts the rest to `runner::McpServer`.
- `crates/claude-code-acp/src/runner.rs`: defines `McpServer { name, command, args, env }`. `Claude::start` passes the servers as `{"mcpServers": {name: {command, args, env}}}`, the shape Pi's `mcp.json` and `pi.registerMcpServer` take.
- `crates/acp-bridge/src/lib.rs`: `mcp_command` checks that a command is an absolute path; `parse_mcp` is its only caller. The crate already depends on `serde_json`.
- `crates/claude-code-acp/tests/protocol.rs`: `passes_stdio_mcp_servers_to_claude` checks the `--mcp-config` Claude gets, and `mcp_commands_are_absolute_paths` the refusal of a relative command.
- `crates/oxd/src/session.rs` (around line 707): gives the `ox` server to an agent that advertises `session.mcp.stdio`, and `instructions::text(step, true)` then adds the `ox` tool paragraphs. No change is needed in `oxd`.
- `crates/oxd/src/mcp.rs`: `OxServer::for_session` builds the stdio server `ox` with no env.
- Pi 1.5.2 docs: `docs/mcp.md` and `docs/extensions.md` ("MCP Servers") under `/opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent/`. Registered servers connect when the session starts, last for the session, and are not saved. Server names may contain only letters, digits, `_` and `-`; names that differ only in `-` and `_` count as the same server, and `registerMcpServer` throws for an invalid or clashing name. With `exposure: "direct"` the first prompt waits up to 10 seconds for the server's tools.
- `crates/pi-acp/tests/protocol.rs`: `FAKE_PI` records each start's arguments in `calls`. `initialize`, `new_session`, `resume_request` and `resume_in_new_bridge` send the ACP requests. `a_new_session_starts_pi_and_reports_idle` checks the exact arguments of a Pi started without servers.
- `scripts/smoke-acp.py`: `SmokeRun.check_title_tool` has the agent call `set_title`; `PiRun.checks` leaves it out.

## Decisions

- **Capability.** `initialize` adds `.mcp(acp::McpCapabilities::new().stdio(acp::McpStdioCapabilities::new()))` to the session capabilities, as the Claude bridge does.
- **Shared conversion.** `McpServer` and `parse_mcp` move from `claude-code-acp` to `crates/acp-bridge/src/lib.rs` as `acp_bridge::McpServer` (`#[derive(Clone, Debug)]`, same fields) and `acp_bridge::parse_mcp(servers: Vec<acp::McpServer>) -> Result<Vec<McpServer>, Error>`, with the same refusals and messages. `mcp_command` folds into `parse_mcp`. `McpServer::config(&self) -> Value` returns `{"command", "args", "env"}`, the `mcpServers` entry both harnesses take; `Claude::start` uses it in place of its inline `json!`. `claude-code-acp` imports `acp_bridge::{McpServer, parse_mcp}` and deletes its own copies.
- **Pi's name rules.** `check_pi_names(servers: &[McpServer]) -> Result<(), Error>` in `crates/pi-acp/src/bridge.rs` refuses a name Pi would reject, with `invalid MCP server name: <name>` when the name is empty or has a character other than letters, digits, `_` and `-`, and `duplicate MCP server name: <name>` when it matches an earlier name once `-` is read as `_`. `new_session` and `resume_session` call `acp_bridge::parse_mcp` and then `check_pi_names`.
- **Session.** `Session` gains `mcp_servers: Vec<McpServer>`, as in the Claude bridge. `start_pi` passes `&session.mcp_servers` to `Pi::start`.
- **Pi entries.** `Pi::start` turns the servers into an object of `server.config()` plus `"exposure": "direct"` under each name. The exposure is set in Rust so the protocol tests see it, and the extension only registers what it is given.
- **Extension.** `crates/pi-acp/src/mcp-servers.js`, embedded as `const MCP_EXTENSION: &str = include_str!("mcp-servers.js")` in `pi.rs`:

  ```js
  // Registers the ACP client's MCP servers, which pi-acp passes in
  // PI_ACP_MCP_SERVERS as mcp.json `mcpServers` entries by name.
  export default function (pi) {
    const servers = JSON.parse(process.env.PI_ACP_MCP_SERVERS ?? "{}");
    for (const [name, config] of Object.entries(servers)) {
      pi.registerMcpServer(name, config);
    }
  }
  ```

  It reads the variable on every load, because Pi registers extension servers again each time it loads extensions.
- **Starting Pi.** `Pi::start(cwd, pi_session_id, instructions, mcp_servers: &[McpServer], updates)`. When `mcp_servers` is not empty it calls `write_mcp_extension()` and adds `-e <path>` and `PI_ACP_MCP_SERVERS=<the Pi entries as JSON>` to the command; otherwise the command is unchanged. A failed write fails the start with `failed to write the MCP extension: <error>`, as a failed spawn does.
- **Extension file.** `write_mcp_extension() -> Result<PathBuf, String>` writes `MCP_EXTENSION` to `std::env::temp_dir().join("pi-acp").join("mcp-servers.js")`, creating the directory. It writes `mcp-servers.js.<pid>` first and renames it over the path, so a Pi that another bridge starts at the same moment reads a whole file. Each start with servers writes it again, so the file always matches the running binary and a cleaned temp directory does not matter.
- **Env values.** Pi resolves `${NAME}` and a leading `!command` in `env` values, as it does for `mcp.json`. The bridge passes the client's values unchanged; `oxd`'s `ox` server has no env.

## Check your assumptions

1. **Where the extension file lives.** Kept.
   - **Decided:** One stable file, `<temp dir>/pi-acp/mcp-servers.js`, rewritten through a rename at every Pi start that has servers. On macOS `std::env::temp_dir()` is the per-user `$TMPDIR`.
   - **Consequences:** Nothing is written outside the temp directory and nothing touches `~/.pi` or the project. On a Linux machine with a shared `/tmp`, another user who creates `/tmp/pi-acp` first makes the write fail, and the Pi start fails with it.
   - **Alternative:** A per-start file with a random name (the `tempfile` crate) that `Pi` owns and deletes when it drops, or a per-user cache directory.
   - **Trade-offs:** The stable path needs no cleanup and no new dependency, as requested. A per-start file has no shared path and leaves nothing behind, but adds a runtime dependency and a file per session.
2. **The server list reaches every process Pi starts.** Kept.
   - **Decided:** `PI_ACP_MCP_SERVERS` stays in Pi's environment, which Pi's stdio MCP servers and the model's `bash` commands inherit.
   - **Consequences:** Commands the agent runs can read the `ox` server's command line: the `ox-mcp` path, the daemon socket and the Ox session ID. Any env a client gives an MCP server is visible the same way.
   - **Alternative:** The extension deletes the variable from `process.env` after reading it and keeps the list on `globalThis` for later loads.
   - **Trade-offs:** Leaving it keeps the extension a three-line loop. Removing it hides the list from child processes, at the cost of state the extension carries across reloads.
3. **An `ox` server in the user's Pi config wins.** Kept.
   - **Decided:** The server registers as `ox`, the name `oxd` gives it. Pi's docs say a `mcp.json` server with the same name takes precedence over a registered one.
   - **Consequences:** A user with an `ox` entry in `~/.pi/agent/mcp.json` or a trusted project's `.pi/mcp.json` gets that server instead of Ox's, and `set_title` and status updates silently stop working in their Pi sessions.
   - **Alternative:** Register under a name unlikely to clash, such as `ox-app`, which changes the tool names to `mcp__ox-app__*`.
   - **Trade-offs:** Keeping `ox` matches the Claude bridge and `oxd`'s instructions, which name the `ox` tools. Another name avoids the clash but makes Pi's tool names differ from what the instructions say.
4. **Refusing names Pi would reject.** Kept.
   - **Decided:** `session/new` and `session/resume` fail with invalid params for a name Pi refuses or a duplicate, before Pi starts.
   - **Consequences:** A client sending such a name gets an error instead of a session whose server is missing. The Claude bridge accepts any name, so the two bridges differ here.
   - **Alternative:** Pass every server through and let `registerMcpServer` throw inside Pi, which reports an extension error and starts without that server.
   - **Trade-offs:** Refusing turns a silent missing tool into an error the client sees, for a few lines of checks. Passing through needs no Pi-specific check, but a bad name only shows on Pi's stderr.

## Test plan

In `crates/pi-acp/tests/protocol.rs`:

- `initialize` also asserts that the response's `capabilities.session.mcp.stdio` is an object, so every test checks the capability.
- `a_new_session_starts_pi_and_reports_idle` already checks the exact arguments of a Pi started without servers, so it covers that no `-e` is added.
- `mcp_servers_reach_every_pi_through_the_extension`: the fake Pi also appends `$PI_ACP_MCP_SERVERS` to `servers`. A `session/new` with the stdio server `ox`, command `/usr/local/bin/ox-mcp`, args `["--session", "s1"]` and env `[{"name":"KEY","value":"value"}]` starts Pi with `--mode rpc --approve --session-id <id> -e <path>`, where `<path>` holds exactly `include_str!("../src/mcp-servers.js")`, and `servers` holds `{"ox":{"command":"/usr/local/bin/ox-mcp","args":["--session","s1"],"env":{"KEY":"value"},"exposure":"direct"}}`. After the bridge is killed, a replacement bridge resumes the session with the same server, and its Pi gets the same arguments and the same JSON.
- `invalid_mcp_servers_are_refused`: on one connection, `session/new` answers `-32602` for an HTTP server, a relative command, the name `o x`, and the pair `a-b` and `a_b`, and starts no Pi. `session/resume` answers `-32602` for a relative command.

The Claude bridge's existing protocol tests, `passes_stdio_mcp_servers_to_claude` and `mcp_commands_are_absolute_paths`, cover the move to `acp_bridge` unchanged.

Live: `make smoke-pi` runs `check_title_tool`, which has the Pi agent call `set_title` and checks the session's title in `oxctl`.

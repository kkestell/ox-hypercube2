## High

### F1. Sparse restored history stalls live subscriptions

High · Broken guarantees · Not fixed · `crates/oxd/src/state.rs:736`

**What's wrong:** Event sequence numbers are treated as vector offsets, although a failed database batch can leave gaps in saved event numbers.

**Evidence:** `crates/oxd/src/state.rs:734` promises “The first events with `seq > after_seq`,” but lines 738–741 implement:

```rust
let start = usize::try_from(after_seq)
    .unwrap_or(usize::MAX)
    .min(events.len());
events[start..].iter().take(BATCH).cloned().collect()
```

`crates/oxd/src/store.rs:375` logs `eprintln!("oxd: writing events: {error}");` and drops the failed batch; subsequent batches keep their original sequence numbers. Restoration reads `MAX(seq)` at `store.rs:192`, and `state.rs:633` assigns `self.events = Some(history)` without renumbering it.

For restored events `[1, 3]`, a subscription from zero sends both and advances its cursor to 3. A newly recorded event 4 occupies vector index 2; `events_after(3)` returns nothing. `crates/oxd/src/session.rs:498` immediately satisfies `.wait_for(|last_seq| *last_seq > after_seq)`, and `crates/oxd/src/conn.rs:208` repeatedly calls it without advancing the cursor. The ordinary desktop subscribes from zero at `crates/ox/src/lib.rs:188`, so this is not limited to explicit nonzero reconnect cursors.

**Consequence:** After a storage failure and daemon restart, the desktop can display saved history and then miss new output. The forwarding task also repeatedly polls without delivering events. Tokio cooperative scheduling means this does not establish an uninterruptible worker or an entirely blocked daemon.

This violates the subscription's sequence-cursor contract for events that still exist and for newly generated output. It does not require restoring dropped events or strengthening the documented database durability guarantee.

The orchestrator traced persistence, restoration, forwarding, and the desktop caller. The state restoration helper at `state.rs:1564` generates dense sequence numbers with `.zip(1..)`. The relevant restoration and slow-subscriber tests in `crates/oxd/tests/daemon.rs` likewise exercise dense histories. `.agents/todo.md` already records the underlying dropped-batch/indexing issue; the from-zero live-subscription consequence above is additional source-established impact of that known defect.

**Proposed fix:** Find the first event whose sequence exceeds the cursor, rather than using the cursor as an array index.

### F2. Cancelling before a Pi dialog arrives leaves the prompt pending

High · Broken guarantees · Not fixed · `crates/pi-acp/src/pi.rs:374`

**What's wrong:** Cancellation withdraws only dialogs already open. A dialog arriving later for the cancelled pending prompt opens normally, while completion of that prompt is needed to consume the cancellation flag.

**Evidence:** `crates/pi-acp/src/pi.rs:196` sets `state.abort_on_start = true`; line 198 calls `state.withdraw_dialogs(Some(&self.input))`. The withdrawal drains only the current dialog map at `pi.rs:58`. In contrast, `pi.rs:392` unconditionally starts a dialog task and line 411 inserts it:

```rust
let task = tokio::spawn(async move {
    let ask = updates.ask(message, schema);
```

```rust
locked.dialogs.insert(id, task.abort_handle());
```

There is no cancellation check in this path. The flag is consumed only by `prompt_answered` at `pi.rs:444`: `let abort = std::mem::take(&mut self.state.lock().unwrap().abort_on_start);`.

The orchestrator independently checked the installed Pi 1.5.2 source under `/opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent/`: `dist/core/agent-session.js:1705` awaits `_tryExecuteExtensionCommand(text)` before reporting the prompt handled; line 1793 awaits `command.handler(args, ctx)`. A handler awaiting a dialog therefore holds the prompt response open. `dist/modes/rpc/rpc-mode.js:349` handles abort by calling `session.abort()`; the dialog promise at lines 51–82 separately awaits its UI response and is not resolved by that RPC abort. `dist/core/agent-session.js:2073`–2083 aborts model/retry/compaction work and waits for idle; it does not cancel the awaited extension handler. The settled notification is emitted by the model-run finalizer at line 1535, which this preflight extension-command path has not entered.

**Consequence:** Pressing Stop while an extension command prepares a dialog can leave a new question visible and the cancelled prompt pending until the user answers or cancels again. A subsequent dialog in the same cancelled command can encounter the same problem.

The trigger is cancellation during ordinary asynchronous preparation in a slash-command handler, before its form opens; no repeated cancellation or restart is needed. It contradicts `pi.rs:185`'s stated behavior, “Stops Pi's run, including the run of a prompt Pi has yet to answer,” and the existing pending-prompt cancellation behavior.

Checked `Bridge::cancel`, daemon prompt state, the desktop Stop action, and Pi protocol tests. `cancel_sent_right_after_prompt_cancels_it` at `crates/pi-acp/tests/protocol.rs:641` covers an ordinary prompt without a dialog; `cancel_withdraws_open_dialogs` at line 859 covers an already-open dialog. Neither exercises the later-dialog sequence.

**Proposed fix:** Immediately cancel newly arriving dialogs while their pending prompt is marked cancelled.

### F3. Speculative background work permanently disables parking

High · Over-engineering · Not fixed · `crates/claude-code-acp/src/background.rs:199`

**What's wrong:** The bridge treats an unreadable or failed scheduling result as background work that must keep Claude alive until it exits. This speculative lifetime policy creates permanent state without establishing that any corresponding work exists. A failed wakeup stop demonstrates the consequence: it creates an unrelated unknown schedule that even a successful retry cannot remove.

**Evidence:** `crates/claude-code-acp/src/background.rs:199` maps an explicit tool error to an unreadable result:

```rust
let readable = (results == 1 && block["is_error"] != true && !result.is_null())
    .then_some(result);
```

`finish` then reaches `None => self.add_unknown(id)` at line 263; `add_unknown` inserts `Kind::Unknown` at line 270. A successful stop at lines 237–240 removes only wakeups:

```rust
("ScheduleWakeup", Some(_)) if call.input["stop"] == true => {
    let before = self.schedules.len();
    self.schedules
        .retain(|s| !matches!(s.kind, Kind::Wakeup { .. }));
```

`turn_ended` retains `Kind::Unknown => true` at line 293. `crates/claude-code-acp/src/updates.rs:160` includes it in published background work; `crates/oxd/src/state.rs:194` requires `self.background.as_deref() == Some(&[])` for an idle session to be quiet and eligible for parking.

**Consequence:** After a failed stop and successful retry, the real wakeup is gone but the idle, unviewed Claude session cannot park until the harness exits.

The trigger is an explicit failed `ScheduleWakeup(stop: true)` result, already represented by existing fixtures, followed by a successful stop. A stop operation cannot create a new wakeup; retaining an unknown schedule for that failure falsely reports background work and defeats the implemented idle-parking rule. The unnecessary guarantee is preserving a process forever because work might exist, rather than tracking work the harness actually established.

The orchestrator traced creation, successful-stop cleanup, publication and daemon parking. The unit test at `background.rs:521` expects the failed stop to add a schedule, then calls `background.clear()` at line 537 before testing successful stopping, missing the retry sequence. `crates/claude-code-acp/tests/protocol.rs:3184` likewise expects the phantom `_claude_schedule:wake-2` after failure.

**Proposed fix:** Remove permanent unknown-schedule bookkeeping; report established harness tasks and successfully parsed schedules without inventing work from unreadable or failed results.

### F4. Model keyboard navigation moves the active option offscreen

High · Broken guarantees · Not fixed · `ui/src/features/composer/ModelPicker.tsx:51`

**What's wrong:** The searchable model menu changes its active option without scrolling it into view.

**Evidence:** `ui/src/features/composer/ModelPicker.tsx:53` advances on Arrow Down; lines 59–61 prevent native handling and focus an option only in the nonsearchable case:

```tsx
event.preventDefault();
setActive(next);
if (!searchable) (list.current!.children[next] as HTMLButtonElement | undefined)?.focus();
```

Searchable menus keep focus in the search input at line 92, advertising the active choice through `aria-activedescendant` at line 113. No handler or effect scrolls that option. `ui/src/styles/controls.css:182` sets `max-height: var(--menu-list-max-height)` and line 183 sets `overflow: auto`; `ui/src/styles/tokens.css:77` caps the height at `40vh`. Enter chooses `models[active]` at `ModelPicker.tsx:57`.

**Consequence:** In a long catalogue, repeated Arrow Down presses move the active choice beyond the visible list. Enter can select a model the user cannot see.

The trigger is ordinary keyboard navigation in a searchable catalogue with enough models to overflow the existing height limit. The implemented navigation changes which model Enter will select, but fails to keep that choice visible; this is a defect in the existing picker behavior, not a request to support a new scale or platform.

The orchestrator checked the complete picker, its Composer caller, model options supplied by the Pi bridge, and the scrolling CSS. `ui/e2e/specs/model.e2e.ts:115` covers keyboard selection only with two options and no search. The command-completion component already scrolls its active option explicitly at `ui/src/features/composer/CommandInput.tsx:52`; no equivalent exists in the model picker. No browser reproduction ran.

**Proposed fix:** Scroll the active model option into view while keeping focus in the search input.

## Medium

### F5. Pi smoke run does not control its transcript location

Medium · Broken guarantees · Not fixed · `scripts/smoke-acp.py:1056`

**What's wrong:** The smoke run leaves its transcript location to inherited Pi configuration while its model-verification step assumes the default directory. The test should choose one location for the run and use it consistently; accommodating arbitrary personal storage layouts is not a requirement.

**Evidence:** `scripts/smoke-acp.py:234` uses `self.env = os.environ.copy()`. `PiRun.verify_model`, included in `checks()` at line 994, resolves `PI_CODING_AGENT_DIR` and then searches at lines 1059–1061:

```python
transcript = next(
    (agent_dir / "sessions").glob(f"*/*_{session['piSessionId']}.jsonl")
)
```

`crates/pi-acp/src/pi.rs:93` launches Pi with the inherited environment and no session-directory override. The orchestrator checked installed Pi 1.5.2 `dist/config.js:496`, which defines `PI_CODING_AGENT_SESSION_DIR`, and `dist/main.js:599`–602, which chooses the session directory from CLI, environment, or `settings.sessionDir`. The latter setting is read at `dist/core/settings-manager.js:534`. None of these alternative directories is considered by the smoke lookup.

**Consequence:** With `PI_CODING_AGENT_SESSION_DIR` pointing outside the default sessions tree, a working run saves its transcript there while verification searches the default tree and raises `StopIteration`. This gives misleading regression feedback after the model work has already run. This establishes inconsistent test setup, not an obligation to discover or support every user configuration. The project's testing guidance also calls for tests to own their temporary configuration and state.

**Proposed fix:** Set `PI_CODING_AGENT_SESSION_DIR` to a directory owned by the smoke run and read the transcript from that directory.

### F6. Client retains handshake state for an unused accessor

Low · Dead code · Not fixed · `crates/ox-protocol/src/client.rs:148`

**What's wrong:** The client retains the hello response only to support an accessor with no consumers.

**Evidence:** `crates/ox-protocol/src/client.rs:148` stores `hello: HelloResult`. Lines 278–281 initialize placeholder protocol/version values, and lines 283–287 replace them with the handshake response. The sole read at lines 314–316 is:

```rust
pub fn daemon_version(&self) -> &str {
    &self.hello.daemon_version
}
```

The orchestrator independently searched all crate source/tests, UI source/tests, scripts and current docs: no caller uses `daemon_version()`, and no other code reads the retained `hello` field. The handshake response type itself remains used by the daemon and tests.

**Consequence:** Each client carries unused state, an unused public accessor and placeholder construction steps.

**Proposed fix:** Remove the accessor and retained field while continuing to deserialize the handshake response.

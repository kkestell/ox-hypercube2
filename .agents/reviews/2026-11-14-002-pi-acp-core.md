## F1. A prompt Pi rejects still titles the session

Low · Correctness · Not fixed · `crates/pi-acp/src/bridge.rs:147`

`Bridge::prompt` sets the session title from the prompt's text as soon as the prompt is sent, before Pi answers. When Pi answers `success:false`, the prompt never enters the conversation, but the session keeps the title taken from it, and the next prompt that Pi accepts does not retitle it.

Pi rejects prompts in ordinary setups: no model selected, no API key for the provider, or compaction in progress. A user's first prompt in a Pi without a configured model therefore names the session after text that is not in its conversation. `claude-code-acp` titles the same way, and the plan asks for titling "as in `claude-code-acp`".

### Evidence

`bridge.rs:137-163`: `pi.prompt` queues the command and returns `Ok`, then the title is set and `session_info_update` sent. Pi's preflight errors are thrown in `AgentSession.prompt` (`agent-session.js:1649`, `1667`, `1680-1691`) and reach the bridge as `success:false`, which `Output::prompt_answered` turns into an error response without touching the title.

### Fix

Not fixed, as instructed for Low findings.

## F3. `Updates` locks a mutex that only one task uses

Low · Simplicity · Not fixed · `crates/pi-acp/src/updates.rs:25`

`Updates` keeps `working` and the open tool calls in a `Mutex<State>` and takes `&self` everywhere. Each `Updates` is moved into one `Output` and used only by that `Output`'s reader task; the bridge never holds it. Methods taking `&mut self` on plain fields would express the same state without the lock. The cost is small; the lock suggests sharing that does not happen.

### Fix

Not fixed, as instructed for Low findings.
